# data/raw

This folder holds the HiRISE elevation and imagery for the EVA site, clipped to the
box in [`../site.json`](../site.json) (M04). Everything here except this README
is generated by [`scripts/fetch-clip.ts`](../../scripts/fetch-clip.ts) and is
git-ignored. Don't commit rasters.

## Outputs

| File            | Contents                                  | Resampling | Nodata            |
| --------------- | ----------------------------------------- | ---------- | ----------------- |
| `elev_5m.tif`   | Elevation (m), Float32                    | bilinear   | -3.4028235e+38    |
| `ortho_5m.tif`  | HiRISE RED ortho image                    | average    | 0                 |
| `ti_5m.tif`     | Thermal inertia (optional), Float32       | bilinear   | -9999             |
| `slope_5m.tif`  | Slope (degrees), Float32 (M09)            | Horn 3×3   | none (checked)    |
| `sand_5m.tif`   | Sand: mapped aeolian bedforms, Byte (M12) | rasterized | none (0 = not)    |
| `soft_5m.tif`   | Soft ground: TI < 200, Byte (M12)         | from TI    | none (0 = not)    |
| `smooth_5m.tif` | Smooth / Us units, Byte (M12, unused)     | rasterized | none (0 = not)    |

All outputs share one grid: 600 × 600 cells at 5 m, covering the
site.json bounds exactly. They are GeoTIFFs with DEFLATE compression and tiling.

The script fails if `elev_5m.tif` or `ortho_5m.tif` has any nodata cell, which
means the site box isn't fully inside the source's valid data. The thermal
inertia layer is best effort. If it fails, the script only prints a warning.

## Slope (M09)

`slope_5m.tif` is generated from `elev_5m.tif` with `gdaldem slope -compute_edges`
(Horn's method). The grid is in metres, so no `-s` scale is needed. Run:

```sh
npm run compute:slope   # after npm run fetch:clip
```

The script fails unless the slope raster has the same size, geotransform and CRS
as `elev_5m.tif` and no nodata cells. It finds GDAL the same way as
`fetch:clip`. `hornSlopeDeg` in `scripts/compute-slope.ts` implements the same
maths in TypeScript, including GDAL's edge handling, for tests and for later
steps that need slope without GDAL (M16, `cost.bin`). It matches gdaldem to
within 0.003° on every cell.

## Sand and soft ground (M12)

```sh
npm run compute:sand   # after npm run fetch:clip
```

`compute:sand` writes three Byte masks (1 = yes, 0 = no). It fails unless each
one has the same size, geotransform and CRS as `elev_5m.tif`.

1. **`sand_5m.tif`: the primary sand mask.** It's the aeolian-bedform units
   from the Stack et al. (2020) photogeologic map, rasterized onto the
   elevation grid. The map units are Ab-l and Ab-s (§4.1). In the shapefile's
   `SurfUName` field they're spelled `Aeolian bedforms, large` and
   `Aeolian bedforms, small`. GDAL reprojects the shapefile (eqc, `lat_ts=0`)
   onto our grid. A cell counts when its centre is inside a polygon.
   `fetch:clip` downloads the map (Springer ESM Online Resource 3, 3.5 MB)
   into `src/`, and GDAL reads it in place via `/vsizip/`.
2. **`soft_5m.tif`: the secondary soft-ground mask.** It's THEMIS thermal
   inertia (`ti_5m.tif`) below `SOFT_GROUND_TI_MAX = 200` J m⁻² K⁻¹ s⁻½ in
   `src/engine/model.ts`. A cell exactly at 200 isn't soft, and nodata is
   never soft. It's an **estimate**: no published cut-off for loose sand
   exists (see the comment on the constant). It's kept separate from
   `sand_5m.tif`, and M16 decides the cost weights.
3. **`smooth_5m.tif`** (optional, not used yet) holds the smooth / Us mantle
   units: `Undifferentiated smooth`, `Minor Cover Us` and `Moderate Cover Us`.

These numbers for the M04 box were **computed by us** (`npm run compute:sand`).
They aren't published values:

| | Share of cells |
| --- | --- |
| Map polygons cover | 99.996% (15 cells fall outside every polygon and count as not sand) |
| Sand (mapped bedforms) | 26.65% |
| Soft ground (TI < 200) | 15.78% |
| Mapped bedforms that are also TI < 200 | 27.34% |
| TI < 200 cells that are mapped bedforms | 46.17% |

The THEMIS map has 100 m pixels, which is why TI on its own matches the mapped
bedforms poorly, and why the geologic map is the primary sand source.

## Exported grid (M16)

```sh
npm run export:grid   # after fetch:clip, compute:slope, compute:sand
```

`scripts/export-grid.ts` writes the real grid to `public/data/` in the M01
formats (`src/contracts.ts`). Those files are committed, because the app
loads them. The layout is row-major, with index = y·width + x and y = 0 as
the north row:

| File | Contents |
| --- | --- |
| `meta.json` | `GridMeta`: 600 × 600, `cellSizeM` 5, `maxSlopeDeg`, and the `habitat` cell converted from `site.json` |
| `cost.bin` | Float32 little-endian; `Infinity` means blocked |
| `elevation.bin` | Float32 little-endian, metres (from `elev_5m.tif`) |
| `sand.bin` | Uint8, 1 = mapped sand (from `sand_5m.tif`) |

Cost uses the same formula as the fixture grid, plus a soft-ground term
(`buildCost`):
`slope > MAX_SLOPE_DEG ? Infinity : (1 + 3·(slope/MAX_SLOPE_DEG)²) × (sand ? SAND_COST_MULT : 1) × (soft && !sand ? SOFT_COST_MULT : 1)`.
The constants are in `src/engine/model.ts` (25°, ×2, ×1.3) and are all
estimates. `public/data/stops.json` isn't written by this script. It only
reports where each stop lands.

## Basemap (M20)

```sh
npm run export:basemap   # after npm run fetch:clip
```

`scripts/export-basemap.ts` warps the full-resolution HiRISE ortho (the
`.LBL`/`.JP2` in `src/`, not `ortho_5m.tif`) onto the extent and CRS of
`elev_5m.tif`, at 1500 × 1500 px (2 m/px, `-r average`). It stretches the
contrast between the 2nd and 98th percentiles to 1–255, so 0 only ever means
"no image data", and writes `public/data/basemap.png` as 8-bit greyscale with
no world file. That file is committed.

Row 0 of the PNG is the north edge, and the image covers exactly the
600 × 600 grid. The script checks the extent to 0.01 m, checks the PNG size,
and fails if any row or column is entirely nodata. It drops to 1200 × 1200 if
the PNG would go over 3 MB.

## CRS

- **Site box:** `site.json` uses planetocentric lat/lon in degrees, with
  longitude east-positive, on the IAU Mars 2000 sphere (R = 3,396,190 m).
- **Sources:** each source keeps its own CRS. The DTM is equirectangular with
  `lat_ts=0, lon_0=0`. GDAL reads the ortho's map projection from its PDS
  `.LBL`, falling back to the JP2's embedded georeferencing. The script doesn't
  force a source CRS.
- **Outputs:** equirectangular, true scale at the box's middle latitude:

  ```
  +proj=eqc +lat_ts=<midLat> +lat_0=0 +lon_0=0 +R=3396190 +units=m
  ```

  `midLat = (minLat + maxLat) / 2` from site.json (18.465° for M04). This keeps
  5 m cells close to square on the ground across the 3 km box.
  Projected x = R · lon · cos(midLat) and y = R · lat, with lon and lat in radians.

## Regenerate

The script works the same on Windows, macOS and Linux. You need Node (the
repo's version) and GDAL ≥ 3.2 with a JPEG2000 driver (JP2OpenJPEG). See below
for installing GDAL.

```sh
npm run fetch:clip
# skip the optional thermal inertia layer:
npm run fetch:clip -- --skip-ti
```

The script reads the bounds from `data/site.json` only, so if the site changes,
re-run it. Clipped outputs are always rebuilt.

## Installing GDAL

The script looks for GDAL in this order:

1. The `GDAL_BIN` environment variable: a folder containing `gdalwarp`. If it's
   set but wrong, the script stops instead of searching further.
2. `PATH`.
3. Common install locations:
   - **Windows:** `C:\Program Files\QGIS*\bin`, `C:\OSGeo4W\bin`, `%CONDA_PREFIX%\Library\bin`.
   - **macOS:** `/Applications/QGIS*.app/Contents/MacOS/bin`, `/opt/homebrew/bin`, `/usr/local/bin`.
   - **Linux:** `/usr/bin`, `/usr/local/bin`, `$CONDA_PREFIX/bin`.

| OS | Install | Notes |
| -- | ------- | ----- |
| Windows | `winget install OSGeo.QGIS` | Bundles GDAL. You need QGIS anyway to check the outputs, and the script finds it automatically. OSGeo4W (https://trac.osgeo.org/osgeo4w/) also works. |
| macOS | `brew install gdal` | The QGIS `.app` (https://qgis.org/download/) also works and is found automatically. |
| Linux (Debian/Ubuntu) | `sudo apt install gdal-bin` | On other distros, use the equivalent package. |
| Any OS | `conda install -c conda-forge gdal` | Activate the environment before running the script. |

To check the install, run `gdalinfo --version` and look for `JP2OpenJPEG` in
`gdalinfo --formats`.

## Viewing in QGIS

1. Use *Layer → Add Layer → Add Raster Layer* and pick `elev_5m.tif`, then `ortho_5m.tif`.
2. Both layers use the custom Mars equirectangular CRS above. Set the project CRS to
   either layer's CRS, using *Project → Properties → CRS* or the CRS button at
   the bottom right, so QGIS doesn't try to reproject to an Earth CRS.
3. Style `elev_5m.tif` as *Singleband pseudocolor* or add a *Hillshade*.
   The two layers should line up: the delta front scarp in the ortho should
   match the elevation step in the DTM.

QGIS may write `*.aux.xml` sidecar files here. They're git-ignored.
